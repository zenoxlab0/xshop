## Round 2 — information architecture + the uploaded emoji pack

### Emoji resolution (`src/utils/embeds.js`)

The bot now renders with the **782 emojis uploaded to this application**:

| File | What it holds |
| --- | --- |
| `src/utils/uiEmojis.json` | UI key → curated custom emoji (`<:name:id>`, 38 keys) |
| `src/utils/uiEmojiFallbacks.json` | UI key → component-safe **unicode** emoji |
| `src/utils/applicationEmojis.json` | legacy synced set, kept as a lower-priority fallback |

Resolution order for every UI key:

1. admin override in `settings` (`!setemoji` / dashboard)
2. **curated pack** — `uiEmojis.json`
3. auto-matched server emoji / legacy `applicationEmojis.json` aliases
4. built-in fallback, then unicode

**`eComp(key, fallback?)` no longer returns `undefined`.** It returns a usable
custom emoji or a validated unicode emoji, always. This was a real crash:
`ButtonBuilder.setEmoji(undefined)` throws
`ValidationError: Expected the value to be an object…`, which took down shop
category/product browsing at `src/shop/views.js`.

> ⚠️ Verified empirically against this project's discord.js:
> **both `setEmoji(undefined)` *and* `setEmoji(null)` throw.** A button with no
> emoji is made by *not calling* `setEmoji` — use the `setCompEmoji(builder, …)`
> helper, which does exactly that and falls back to `⭐` if needed.

`validEmojiValue()` (not `parseEmoji()` alone) gates every component emoji, so
plain-text symbols such as `✦` or `₿` are rejected rather than forwarded to
Discord as `COMPONENT_INVALID_EMOJI`.

Curated ids are trusted as usable *before* `loadAppEmojis()` resolves (the
`CURATED_IDS` set), so the shop never flashes unicode fallbacks on boot.
All 782 ids are returned by a single unpaginated
`GET /applications/{id}/emojis`, so `loadAppEmojis()` sees all of them.

### Screen-by-screen information architecture

The rule: **the list shows what you can buy; the detail page shows everything
about it.** The category screen used to print a stock badge and a truncated
description under every product — 18 lines for 9 products, and the details had
to be re-read on the next screen anyway.

| Screen | Now shows |
| --- | --- |
| `shopPanel` | categories, one line each + trust row |
| `categoryMenu` | **name + price + availability only**, as an inline-field grid (Discord aligns it, 3 per row); descriptions and limits removed |
| `productDetails` | full description, stock, delivery, quantity range, checkout-question count |
| `!help` | customer guide: order steps, status legend, good-to-know |
| `!xhelp` | **interactive console** — overview + one screen per section, driven by a `help:section` select menu |

`!xhelp` details:

- new file `src/commands/xhelp.js`; `!xhelp` posts the overview
- `interactionCreate.js` routes `help:section` → `xhelp.handleSelect()`
- **every one of the 39 registered commands has a one-line description**
- commands not filed under a section fall through to *System*, so a command
  added later can never disappear from the reference
- non-staff get an ephemeral refusal; bogus section ids fall back to *System*
- select placeholder/labels/descriptions go through `plain()` (emoji go in `emoji:`)

## Premium UI kit (`src/utils/embeds.js`)

Every screen is built from one shared kit so the look stays consistent:

| Helper | Purpose |
| --- | --- |
| `heroLines(subtitle)` | Brand header + divider — the top of every panel |
| `section(label)` | Uppercase section heading inside an embed |
| `kv(label, value)` | Fixed-width label/value row |
| `progressBar(done, total)` | `▰▰▰▰▱▱▱ 4/7` tracker used by `progressTracker()` |
| `DIV` / `DIV_SOFT` / `BULLET` / `DOT` | Dividers and bullet glyphs |
| `plain(text)` | **Plain-text sanitiser** — see the rule below |

### ⚠️ Custom emoji rule (this caused a visible UI bug)

Discord renders **select-menu placeholders, option labels/descriptions, button
labels and modal field labels/placeholders as PLAIN TEXT** — a custom-emoji tag
such as `<:MekoFastMessage:1551781841235873834>` is shown **literally**
(that is how it leaked into “Choose your payment method…”).

* Embed `title` / `description` / `fields` / message `content` → custom emoji ✅
* Select placeholder / option text / button label / modal text → **`plain(...)`**
  and put emojis in the dedicated `emoji:` field / `.setEmoji()` instead.

`npm run smoke` enforces this: *“no raw emoji tags in plain-text component
fields”* builds every storefront/flow component and fails if any plain-text
field contains an emoji tag.
